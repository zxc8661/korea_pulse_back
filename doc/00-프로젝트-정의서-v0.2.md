## 요구사항 · 역할 분담 · 수익화 계획 v0.2

- 작성일: 2026-09-14
- 문서 상태: 팀 검토용 초안

## 1. 프로젝트 목적

Korea Pulse는 수집한 국내 뉴스에서 관심이 증가하는 이슈를 탐지하고, 관련 기사와 시간별 변화를 보여주는 웹 서비스다.

**핵심 메시지: 지금 대한민국이 무엇에 주목하고 있는지 한눈에.**

초기 서비스 설명에는 “수집한 뉴스 기준”이라는 분석 범위를 함께 표시한다. 뉴스 언급량은 국민 전체의 관심이나 여론을 직접 측정한 값이 아니다. 검색 관심도는 확보 가능한 일 단위 보조 지표로 제공한다.

사용자는 주요 이슈 확인 → 관심 이슈 선택 → 증가 시점과 관련 기사 확인의 흐름으로 서비스를 이용한다.

## 2. 제품 가치와 사용자

| 사용자 | 필요한 정보 | 제공 가치 |
|---|---|---|
| 일반 사용자 | 짧은 시간에 오늘의 이슈 파악 | 급상승·언급량 순위와 대표 기사 |
| 분야 관심 사용자 | 경제·스포츠 등 특정 분야 변화 | 카테고리 필터와 시간별 추이 |
| 향후 유료 고객 | 자사·경쟁사·제품 관련 보도 변화 | 키워드 모니터링, 변화 알림, 브리핑 |

차별화 가설은 이슈 단위 탐색, 증가 이유의 근거 제시, 간결한 모바일 UX, 작은 팀도 구매할 수 있는 모니터링 상품이다. 경쟁 서비스보다 빠르거나 정확하다는 주장은 비교 측정 후 사용한다.

## 5. 데이터 소스 전략

데이터 소스는 세 가지다. 역할이 서로 다르며 서로를 대체하지 않는다.

| 소스 | 역할 | 상태 |
|---|---|---|
| NAVER News Search API | 이슈 탐지의 **메인 코퍼스**. 언급량·증가율·Hot Score의 유일한 입력 | 접근 조건 확인됨. 약관 확인 필요 |
| YouTube Data API v3 | ① 신규 키워드 유입 ② 이슈별 **영상 관심도** 보조 지표 | 키 발급 가능. 쿼터 제약 심각(5.2) |
| Google Trends API | 이슈별 **검색 관심도** 보조 지표 | **알파 신청제**. 접근 미확보(5.3) |

보조 지표는 둘 다 Hot Score와 순위 계산에 들어가지 않는다. 이유는 §8에 있다.

### 5.1 NAVER News Search API (메인 코퍼스)

뉴스 수집과 이슈 상세의 관련 기사를 모두 이 API로 처리한다. 공식 응답의 제목, 요약, 원문·네이버 링크, 게시 시간을 활용한다. 언론사명은 별도 매핑이 필요할 수 있어 임의로 추정하지 않는다. [NAVER 뉴스 검색 API](https://developers.naver.com/docs/serviceapi/search/news/news.md)

| 항목 | 값 |
|---|---|
| 일 호출 한도 | 25,000회 |
| 호출당 결과 | 최대 100건 (`display=100`) |
| 정렬 | `sort=date` (최신순) |

저장·캐시·재표시·상업 이용 범위는 적용 약관 확인 후 정한다. 기사 본문 재배포 권한을 API 접근 권한과 동일하게 취급하지 않는다.

### 5.2 YouTube Data API v3 (영상 신호)

지정된 키워드로 영상을 검색해 수집하는 방식은 **불가능하다**. 공식 문서 기준 기본 할당이 아래와 같기 때문이다.

| 항목 | 값 |
|---|---|
| `search.list` | **하루 100호출** (별도 쿼터 버킷) |
| 그 외 엔드포인트 합산 | 하루 10,000 units |
| `videos.list`, `playlistItems.list` | 호출당 1 unit |

15분 주기(하루 96런)에 키워드 150개를 검색하려면 하루 14,400회가 필요하다. 허용치의 144배다. 따라서 **`search.list`를 쓰지 않는** 설계를 선택한다.

대신 1 unit짜리 두 경로만 쓴다.

- **국내 인기 영상**: `videos.list?chart=mostPopular&regionCode=KR&videoCategoryId=...`
- **뉴스 채널 업로드**: `playlistItems.list`로 지정 언론사 채널의 업로드 플레이리스트 조회

이 방식은 하루 약 2,000 units로 한도의 20% 수준이다. 다만 **이슈별 커버리지가 균등하지 않다**. 인기 차트와 채널 업로드에 잡히는 이슈만 영상이 붙고 나머지는 0이다. 그래서 영상 수를 언급량에 합산하거나 Hot Score에 넣지 않는다(§8). 상세 화면의 보조 지표로만 쓴다.

YouTube에는 “경제” 카테고리가 없다. 경제 이슈의 영상은 인기 차트가 아니라 뉴스 채널 업로드로 커버한다. [YouTube Data API 쿼터](https://developers.google.com/youtube/v3/getting-started#quota)

영상 섬네일·제목·채널명·조회수만 저장하고 영상을 재생하거나 다운로드하지 않는다. 노출은 YouTube 링크아웃 또는 공식 임베드로만 한다.

### 5.3 Google Trends API (검색 관심도)

검색 관심도는 Google Trends API에서 받는다. 다만 **2025년 7월 공개 이후 지금까지 알파이고 신청 승인제**다. 승인 전에는 데이터가 없다고 가정하고 설계한다. [Google Trends API 알파](https://developers.google.com/search/apis/trends)

| 항목 | 값 | 설계 영향 |
|---|---|---|
| 접근 | 알파 신청제 | 미승인 상태에서도 서비스가 돌아가야 한다 |
| 집계 단위 | 일·주·월·년 | 시간별 급상승 입력으로 쓰지 않는다 |
| 최신성 | **2일 전까지** | 기준일을 함께 표시한다. 오늘 값이 아니다 |
| 스케일 | 요청 간 **일관된 스케일** | 서로 다른 요청의 값을 이어 시계열로 그릴 수 있다 |
| 범위 | 최근 1,800일 | MVP에는 충분 |
| 지역 | 국가·하위지역(ISO 3166-2) | 한국(KR)으로 고정 |

일관된 스케일은 기존 NAVER DataLab 대비 명확한 이점이다. DataLab은 요청마다 0~100으로 재정규화해 서로 다른 조회 결과를 이을 수 없었다.

데이터가 없거나 알파 접근이 없으면 null과 사유를 반환하고 “검색 데이터 없음”으로 표시한다. 오늘의 실시간 검색량으로 표현하지 않는다.

### 5.4 채택하지 않은 소스

| 소스 | 사유 |
|---|---|
| 빅카인즈 | 웹 기능과 동일한 API 제공 여부·상업 이용 조건이 불투명하고, 2인 팀이 계약 협의로 시간을 쓸 여유가 없다. 네이버 뉴스로 MVP 검증이 가능하다 |
| GDELT | 국내 매체 커버리지가 검증되지 않았고, 해외의 한국 보도 분석은 MVP 범위 밖이다 |
| NAVER DataLab | Google Trends와 역할이 중복이고, 요청마다 재정규화되어 시계열로 이을 수 없다 |

빅카인즈는 유료 상품 단계에서 다시 검토한다. 메인 공급원을 네이버로 확정했지만 `NewsProvider` 인터페이스는 그대로 둔다.

## 6. MVP 범위와 우선순위

원안의 6개 탭을 목표로 유지한다. 전체는 카테고리 자체가 아닌 통합 조회다.

| 코드 | 표시명 |
|---|---|
| ALL | 전체 |
| ECONOMY | 경제 |
| SPORTS | 스포츠 |
| ENTERTAINMENT | 연예 |
| POLITICS_SOCIAL | 정치/사회 |
| IT_SCIENCE | IT/과학 |

2인 팀의 첫 검증은 경제·스포츠 표본부터 진행하는 것을 제안한다. 공개 시점의 전체 탭은 실제로 수집·분류하는 범위를 명시한다.

| 우선순위 | 기능 | 완료 기준 |
|---|---|---|
| P0 | 뉴스 파이프라인 | 재수집해도 중복 집계되지 않음 |
| P0 | 이슈 클러스터 | 대표 기사로 제목과 주제를 설명할 수 있음 |
| P0 | 급상승·언급량 순위 | 정렬 기준·비교 기간이 표시됨 |
| P0 | 카테고리 필터 | 해당 범위의 데이터와 동일한 기간 적용 |
| P0 | 이슈 상세 | 추이·연관 키워드·대표 기사·집계 시각 제공 |
| P0 | 검색 | 기존 이슈 제목·별칭·연관 키워드 검색 |
| P0 | 상태 처리 | 로딩·빈 결과·오류·지연 데이터 표현 |
| P1 | Trend Bubble | 목록과 동일 데이터, 터치·키보드로 상세 이동 |
| P1 | 영상 관심도 | 관련 영상 수·조회수·대표 영상. 커버리지 한계를 명시 |
| P1 | 검색 관심도 보조 그래프 | 일 단위·기준일 표시. Trends 알파 승인 전에는 비활성 |

기간은 1h·6h·24h·7d를 목표로 한다. 이전 비교 기간까지 데이터가 확보된 옵션만 활성화한다. 7d 증가율에는 원칙적으로 현재 7일과 이전 7일 데이터가 필요하다.

MVP 이후: 회원가입, 결제, 자동 알림, 개인화, AI 요약, 댓글·커뮤니티, 모바일 앱, 글로벌 비교.

## 7. 화면과 디자인 요구사항

### 메인

헤더·검색 → 서비스 설명·최근 갱신 시각 → 카테고리·기간 → 급상승 순위 → 많이 언급됨 순위 → 버블 시각화 순으로 구성한다. 버블은 주요 이슈를 탐색하는 보조 도구다.

순위 항목에는 이슈명, 카테고리, 증가율 또는 중복 제거 기사 수, Hot Score, 짧은 근거를 표시한다. 예시 문장은 “최근 1시간 42건, 이전 1시간 12건”처럼 실제 집계로 생성한다.

### 이슈 상세

이슈명·요약 지표 → 뉴스 언급량 추이 → 증가 근거 → 대표·관련 기사 → 연관 키워드 → 선택적 보조 지표(검색 관심도·영상 관심도) 순서다. 뉴스 수·검색 지수·영상 조회수는 단위가 모두 달라 별도 그래프로 보여준다.

보조 지표에는 출처와 한계를 함께 적는다. 검색 관심도는 “2일 전 기준”, 영상 관심도는 “인기 차트·뉴스 채널 기준이라 모든 이슈에 있지는 않음”을 밝힌다. 영상은 링크아웃 또는 공식 임베드로만 제공한다.

### 검색

검색은 추적 중인 이슈 탐색부터 지원한다. 검색되지 않은 키워드의 Hot Score를 임의 생성하지 않는다. 미추적 키워드는 “아직 분석 중인 이슈가 없습니다”와 관련 뉴스 탐색 경로를 제공한다.

### 시각화·접근성

버블 면적을 언급량에 비례시키고 범례를 제공한다. 색상만으로 급상승 여부를 전달하지 않는다. 이동 애니메이션은 읽기를 방해하지 않으며 모션 감소 설정을 지원한다. 차트는 누락 구간과 실제 0을 구분하고 수치 확인 수단을 제공한다.

## 8. 이슈 분석과 지표

### 중복 제거와 클러스터

URL 정규화·공급자 ID로 동일 기사를 제거하고, 제목·허용된 텍스트 유사도로 재배포 기사를 묶는다. 원본 기사 수와 중복 제거 후 기사 수를 구분한다.

기업명이 같다는 이유만으로 다른 사건을 모두 합치지 않는다. 예를 들어 삼성전자 실적 발표와 HBM 공급 계약은 문맥·시간에 따라 별도 이슈가 될 수 있다. 대표 카테고리 1개와 보조 태그를 두고 미분류 상태를 허용한다.

### 기간과 증가율

현재 구간은 [T-P, T), 비교 구간은 [T-2P, T-P)로 맞춘다. T는 완료된 공통 집계 시점, P는 선택 기간이다. 저장 시각은 UTC, 화면은 KST로 표시한다.

이전 기사 수가 양수일 때 증가율 = (현재 - 이전) / 이전 × 100.
이전 0건이면 증가율 null과 “신규”를 표시한다. 비교 데이터가 부족하면 “비교 데이터 부족”으로 구분한다.

소량 기사의 과장된 증가율을 막기 위해 최소 기사 수·출처 수 조건과 완화된 증가량 지표를 평가한다. 임계값은 표본 검토 후 확정한다.

### Hot Score 제안

원안 가중치는 증가율 35%, 언급량 20%, 검색 관심도 20%, 출처 다양성 10%, 신규성 10%, 지속성 5%다.

권장 MVP는 보조 지표를 전부 분리하고 뉴스 항목만 동일한 방식으로 계산한다. 초기 실험 가중치는 증가율 45%, 언급량 30%, 출처 다양성 15%, 신규성 10%다. 이는 확정 알고리즘이 아니다.

**검색 관심도와 영상 관심도는 점수에 들어가지 않는다.** 둘 다 같은 이유다. 이슈마다 데이터 유무가 갈리는데, 있는 이슈에만 가산하면 데이터 존재 여부가 공지사항처럼 순위에 반영된다.

| 보조 지표 | 불균등의 원인 |
|---|---|
| 검색 관심도 | 상위 이슈만 조회하고, 2일 전 값이라 시간 단위 순위와 기준이 다르다 |
| 영상 관심도 | 인기 차트·뉴스 채널에 잡힌 이슈에만 붙는다. 키워드 검색을 못 쓰므로 커버리지를 균등하게 만들 수가 없다(§5.2) |

각 입력의 정규화 기준, 상한 처리, 기준 집단과 버전을 저장한다. Hot Score는 내부 상대 점수이며 진실성·사회적 중요도·국민 관심 비율을 의미하지 않는다.

## 9. 기술 구조와 저장 모델

예상 스택: Next.js·TypeScript / Spring Boot / PostgreSQL / Redis.

NAVER 뉴스 → Collector → 정규화·중복 제거 → 키워드·클러스터 → 분류·시간 집계 → 점수 → PostgreSQL 스냅샷 → Redis 랭킹 → API → 웹.

YouTube와 Google Trends는 이 주 파이프라인에 끼어들지 않는다. 영상은 후보 키워드 유입과 보조 지표 계산에만, 검색 관심도는 보조 지표 계산에만 붙는다. 두 소스가 전부 죽어도 순위와 상세는 그대로 동작해야 한다.

15분 배치는 목표 주기다. 실제 공급 지연과 호출 한도 확인 후 확정한다. 배치의 실행 간격과 뉴스 발생부터 화면 노출까지의 지연을 각각 측정한다.

| 모델 | 주요 내용 |
|---|---|
| Article | 공급자 ID, URL, 게시·수집 시각, 출처, 허용된 텍스트 |
| ArticleDuplicateGroup | 중복 그룹·대표 기사 |
| Topic / TopicArticle | 이슈와 기사 연결 |
| Keyword / TopicKeyword | 정규화 키워드·별칭·이슈 연결 |
| TrendSnapshot | 구간, 기사 수, 증가율, 출처 수, 점수, 점수 버전 |
| SearchInterestSnapshot | 키워드, 기준일, 일관 스케일 값, 조회 조건 (Google Trends) |
| Video / TopicVideo | YouTube 영상 메타(영상 ID, 제목, 채널, 게시 시각, 조회수)와 이슈 연결 |
| CollectionRun | 수집 성공·실패·지연·처리 건수, 소스별 호출 수 |

Redis Sorted Set의 멤버는 변경 가능한 제목 대신 topicId를 사용한다. hot·growth·mentions 정렬과 category·period·snapshot 버전을 구분한다. 계산 완료된 스냅샷을 일괄 게시해 서로 다른 배치 결과가 섞이지 않게 한다.

## 10. 프론트엔드·백엔드 API 계약 초안

| 경로 | 역할 |
|---|---|
| GET /api/v1/trends?category=ALL&period=1h&sort=growth | 순위 |
| GET /api/v1/topics/{topicId}?period=24h | 상세 |
| GET /api/v1/topics/{topicId}/timeline?period=24h | 시계열 |
| GET /api/v1/topics/{topicId}/articles | 관련 기사 |
| GET /api/v1/topics/{topicId}/related-keywords | 연관 키워드 |
| GET /api/v1/search?q=삼성전자 | 이슈 검색 |

sort는 hot·growth·mentions를 구분한다. 세 정렬은 각각 전체 순위 후보를 대상으로 독립 선정한다. 한 정렬의 상위 N을 재정렬해 다른 정렬을 만들면 급상승 순위가 Hot Score 상위의 부분집합으로 줄어든다. 리스트에는 limit과 페이지 처리 방식을 합의한다.

공통 메타: snapshotId, generatedAt, dataThrough, period, timezone, dataStatus, scoreVersion.
상태: fresh / stale / insufficient.
순위 항목의 주요 값: topicId, title, category, rank, hotScore, mentionCount, previousMentionCount, growthRate, growthStatus, sourceCount, reason.

searchInterest는 순위가 아니라 **이슈 상세 응답에만** 실는다. §5.4·§8이 검색 관심도를 뉴스 점수와 분리한 결정을 응답 계약에서도 그대로 지키는 것이다.

growthRate는 nullable이다. hotScore는 순위 응답에서는 항상 값이 있지만, 순위권 밖 이슈의 상세·검색 응답에서는 정규화 기준을 재현할 수 없을 때 null이 된다. 순위와 상세는 동일 snapshotId 기준으로 읽을 수 있도록 한다. 관련 뉴스 외부 API 실패가 이슈 상세 전체를 실패시키지 않게 한다.

## 11. 운영 품질과 출시 기준

- 메인 API P95 < 500ms 목표. 캐시 적중률·데이터량·동시 요청 조건을 기록하고 검증한다.
- 외부 API 장애 시 마지막 정상 스냅샷과 갱신 지연 표시를 제공한다.
- 부분 수집 실패 구간을 정상 0건으로 계산하지 않는다.
- 배치 재실행은 중복 집계를 만들지 않는다. 재시도 횟수·대기·호출 상한을 관리한다.
- 원문 링크와 출처를 표시하고 공급자별 저장 정책을 적용한다.
- 출시 전 모바일 화면, 키보드 접근, 검색 빈 결과, 뉴스 API 장애, 지연 데이터 상태를 확인한다.

데이터 검증 제안: 우선 24시간 표본으로 상위 20개 이슈와 대표 기사 3건씩을 두 사람이 검토한다. 20개 중 16개 이상이 일관된 주제로 설명되는지 확인하고 오합침·과분리·복제 기사 문제를 기록한다. 이 수치는 초기 내부 기준이며 대표성이나 정확성을 입증하는 통계는 아니다.

## 12. 수익 구조

### 기본 모델

무료 공개 서비스로 유용성과 신뢰를 검증하고, B2B 키워드 워치를 별도 상품으로 판매한다. 유료 고객의 키워드가 공개 순위에서 우대되지 않게 한다.

초기 고객 가설은 소규모 브랜드·스타트업의 PR 및 마케팅 담당자다. 고객은 “기사 목록”보다 “확인해야 할 변화를 놓치지 않는 것”에 비용을 지불하는지 검증한다.

### 가격 실험안

| 상품 가설 | 월 가격 가설 | 제공 범위 가설 |
|---|---:|---|
| Starter | 9만 원 | 키워드 3개, 이메일 알림, 주간 브리핑 |
| Standard | 29만 원 | 키워드 10개, 알림, 일간 브리핑 |
| Pro | 49만 원 | 키워드 30개, 경쟁사 비교, 팀 공유 |

가격·키워드 수·알림 채널은 미확정이다. 첫 판매는 키워드 3개와 주간 브리핑 단일 상품으로 시작하는 것을 권장한다. VAT, 알림 지연, 제공 시간, 해지·환불 조건은 판매 전에 명시한다.

### 판매 검증 순서

1. 잠재 고객 10곳 인터뷰: 현재 모니터링 방법, 놓친 이슈, 사용 시간과 예산 조사.
2. 관심 고객 3곳에 샘플 브리핑 제공. 실제 발송은 고객 동의 후 진행.
3. 유료 파일럿 3곳 확보 후 4주간 운영 시간·유효 알림·오탐·갱신 의사 측정.
4. 반복 구매 근거가 생기면 10개 고객으로 확대.
5. 공통 요구가 확인된 기능부터 로그인·자동 알림·결제 구현.

### 매출과 비용

월 9만 원 상품 10곳이면 월 반복매출은 90만 원이다. 이는 고객 확보를 가정한 산술 예시이며 예상 이익이 아니다.

공헌이익 = 매출 - 데이터 사용료 - 인프라 - 발송·결제 수수료 - 고객별 운영비.
손익분기 고객 수 = 월 고정비 / 고객당 월 공헌이익.

두 사람의 운영 시간도 기록한다. 반자동 브리핑의 수작업 비용을 제외하면 수익성을 과대평가할 수 있다.

## 15. 원안 대비 변경점

- 데이터 소스를 네이버 뉴스 + YouTube + Google Trends 세 개로 확정하고, 빅카인즈·GDELT·DataLab을 제외했다(§5.4).
- YouTube `search.list`가 하루 100호출이라 키워드 검색 수집을 포기하고 인기 차트·채널 업로드 경로로 전환했다.
- 뉴스 급상승과 보조 지표(검색·영상)를 분리하는 MVP안을 제안했다.
- 버블 시각화보다 데이터·순위·상세의 완성을 우선했다.
- 검색 미추적·비교 기간 부족·0건·외부 장애의 표현을 정의했다.
- 2인 역할 분담과 API 계약, 유료 파일럿 검증 절차를 추가했다.
- 이전 초안의 경쟁사 가격·매체 수·API 무료 제공 단정은 채택하지 않았다.

참고 자료는 2026-09-14 공식 페이지에서 확인했다. 데이터 이용 권한과 공급자 계약은 아직 확인되지 않았다.
